# StageOps: решения и ограничения

## Задача

Сервис принимает заказ, резервирует конкретные единицы оборудования и регистрирует нехватку для оператора. Покупатель не занимается разрешением складских конфликтов. Подтверждение означает «заказ получен», а не «поставщик уже подтвердил закупку».

Основная реализация: один Python-сервис и одна PostgreSQL. Интерфейс использует HTTP/JSON и не подключается к базе напрямую. Очередь, Redis и микросервисы не добавлены: в текущем сценарии нет внешних операций, для которых они нужны.

## Почему не счётчик остатков

Модель товара и физическая единица - разные сущности. Для одной модели могут существовать десятки единиц, возвращающихся в разные даты. Простое уменьшение `stock` не отвечает на вопрос о доступности в конкретном интервале.

Начальные занятые единицы имеют `available_from`: дату возвращения из существующего оборота. Новые заказы создают строки в `reservations`. Это упрощение исходной загрузки, а не полная история предыдущих аренд.

Парк из 343 единиц фиксирован для воспроизводимости. В категории звука 118 единиц. Одна KUDO возвращается 17-го числа месяца сценария, остальные - первого числа через три месяца после него.

## Даты

- Бизнес-дата определяется сервером в `Asia/Tashkent`.
- Аренда допускается только с первого числа следующего календарного месяца. Это **не** минимальный запас в 30 дней: в конце месяца возможен старт завтра.
- Выбранный последний день включён в аренду. В базе используется полуоткрытый интервал `[start_date, end_exclusive)`, где `end_exclusive` - следующий день после выбранного окончания.
- Одна единица должна покрывать весь срок. Замена оборудования посередине аренды не поддерживается.
- Общий выбор дат перезаписывает даты всех позиций; затем можно изменить одну отдельно.
- Фикстура остаётся привязана к месяцу создания, но нижняя граница бронирования меняется вместе с реальным временем. «Новый сценарий» обновляет фикстуру после смены месяца.

## Транзакция и одновременные запросы

`main.py` открывает транзакцию через `sessions.begin()` и передаёт её в `booking.place_order()`:

1. Блокируется строка сценария через `SELECT ... FOR UPDATE`.
2. Проверяется ключ повторного запроса и отпечаток содержимого.
3. Проверяются допустимые даты и существование товаров.
4. Создаются заказ и позиции, выбираются свободные на весь интервал единицы.
5. Записываются брони, заявки на недостающее количество и события дефицита.
6. Транзакция фиксируется **до** возврата успешного HTTP-ответа.

Все запросы распределения одного сценария используют одну блокировку. Второй запрос ждёт завершения первого и затем видит его бронь. Разные сценарии блокируют разные строки. Это намеренно грубая, понятная блокировка: для большого склада стоило бы блокировать более узкие группы оборудования с фиксированным порядком захвата.

Дополнительно ограничение PostgreSQL `EXCLUDE USING gist` запрещает пересекающиеся интервалы одной единицы даже при записи в обход сервиса. Оно не подменяет всю бизнес-логику: соответствие товара и сценария проверяется запросом распределения, а не этим ограничением.

Операторский запрос берёт `FOR SHARE` на тот же сценарий, чтобы прочитать согласованную сводку без половины одновременно создаваемого заказа.

## Повторная отправка

Браузер отправляет UUID `requestId`. В базе уникальна пара `(scenario_id, request_id)`; рядом хранится SHA-256 нормализованного содержимого.

- Тот же ключ и те же данные возвращают прежний результат с HTTP 200.
- Тот же ключ с другими данными возвращает HTTP 409.
- Новый заказ возвращает HTTP 201.
- Ошибка до фиксации откатывает весь заказ. После потери ответа повтор с тем же ключом позволяет узнать сохранённый результат.

Хеш здесь нужен для сравнения запроса, не для хранения пароля. Ключ пока сохраняется в памяти вкладки, не между перезагрузками; восстановления черновика после закрытия вкладки нет.

## Закупка не равна наличию

Если доступна одна единица, а заказаны три, создаются одна физическая бронь и заявка на две единицы. Заявка со статусом `requested` не создаёт `assets`. Позднейший заказ может использовать имеющуюся единицу, если первый не смог занять её на весь нужный срок.

Нет поставщиков, реальных платежей, уведомлений и приёмки. При добавлении внешней отправки потребуется надёжная доставка после фиксации транзакции, например таблица outbox и отдельный обработчик. Пока `system_events` является журналом событий, а не готовой очередью сообщений.

## Доступ и демонстрационные данные

Случайная HttpOnly-cookie содержит идентификатор сценария. Данные хранятся на сервере, а не только в состоянии интерфейса. Другой сценарий не расходует этот парк. Cookie является ключом доступа к демонстрации: это не учётная запись и не система ролей.

`/operator` отделён от клиентской навигации. Новый сценарий не удаляет прежние данные. Нет очистки старых сценариев или ограничения их количества, поэтому открытое размещение требует внешнего rate limit и политики хранения.

Автозаполнение использует вымышленные имена, адреса `example.com` и телефонный диапазон `+1 202 555 01xx`. Приложение никому не пишет и не звонит.

## Два варианта запуска

Основной вариант: FastAPI отдаёт собранный интерфейс и обрабатывает `/api/*`, PostgreSQL хранит данные. Второй вариант сохраняет адрес Sites: тонкий прокси отправляет те же запросы в отдельно размещённый Python.

Пока `PYTHON_API_URL` не настроен в Sites, опубликованный прототип использует TypeScript/D1. После включения прокси сбой Python возвращает 503 и **не** переключает запись обратно в D1. Иначе повторный запрос мог бы попасть в другую базу.

Старые данные D1 автоматически в PostgreSQL не переносятся; Python-версия начинает собственные сценарии.
