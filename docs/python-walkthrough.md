# Как устроен StageOps

Этот маршрут предназначен для знакомства с проектом, не для заучивания ответа на собеседование. Начните с одного товара и одного заказа; интерфейс целиком пока разбирать не требуется.

## 1. Что здесь делает Python

Интерфейс рисует экран, собирает корзину и отправляет данные. Python проверяет их, принимает решение о выделении оборудования и сохраняет результат в PostgreSQL. База хранит данные между запросами и дополнительно защищает их ограничениями.

**SQL - язык запросов, PostgreSQL - сама система базы данных.** SQLAlchemy позволяет писать многие запросы через Python-объекты и передаёт SQL в PostgreSQL через драйвер psycopg. Для расчёта склада оставлен также обычный SQL, который можно прочитать напрямую.

В полной Python-версии FastAPI раздаёт уже собранные HTML, CSS и JavaScript. Исходный React не превращается в Python: браузер продолжает выполнять JavaScript, а Python обслуживает HTTP-запросы.

## 2. Где соединяются интерфейс и сервер

Откройте `components/stageops-app.tsx`, функцию `submitOrder`. Она отправляет:

```ts
fetch("/api/orders", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ requestId, contact, items }),
});
```

Это сокращённая форма существующего кода: в компоненте UUID хранится в `requestId.current`. Нажатие кнопки вызывает обычный HTTP-запрос с JSON. Пароль базы и SQL-запросы в браузер не передаются.

В `backend/stageops/main.py` этот адрес обрабатывает функция под декоратором `@app.post("/api/orders", ...)`. FastAPI сначала превращает JSON в `OrderInput`, затем обработчик вызывает `place_order` внутри `sessions.begin()`.

После успешной фиксации возвращаются номер, время и количество единиц. Браузер получает JSON, вызывает `setReceipt` и показывает финальный экран. Клиенту не возвращаются внутренние заявки на закупку.

| Запрос | Назначение |
| --- | --- |
| `GET /api/catalog` | Получить каталог, актуальную дату и cookie сценария |
| `POST /api/orders` | Создать заказ или вернуть результат повтора |
| `GET /api/operations` | Получить склад, заказы и закупки текущего сценария |
| `POST /api/scenario` | Начать новый демонстрационный сценарий |

## 3. Что находится в базе

| Таблица | Одна строка означает |
| --- | --- |
| `products` | Модель оборудования, например KUDO |
| `scenarios` | Изолированную демонстрацию одного браузера |
| `assets` | Одну физическую единицу конкретной модели |
| `orders` | Заказ с контактами и ключом повторной отправки |
| `order_lines` | Позицию заказа: модель, количество и даты |
| `reservations` | Назначение конкретной единицы позиции заказа |
| `purchase_requests` | Заявку на недостающее количество по позиции |
| `system_events` | Зафиксированный факт дефицита |

Один заказ содержит несколько позиций. Одна позиция может получить несколько физических единиц и одну заявку на недостающее количество. Внешние ключи связывают записи и не позволяют сослаться на несуществующий заказ или оборудование.

Структура объявлена в `models.py`. Файл `migrations/versions/0001_initial.sql` содержит SQL, создающий таблицы, индексы и ограничения. Alembic применяет его и запоминает версию схемы. Это отличается от начального наполнения: `catalog.py` вставляет уже сами модели и тестовый парк.

## 4. Как выбирается свободная единица

Главная функция - `backend/stageops/booking.py:place_order`. Для каждой позиции она ищет нужное количество единиц, которые относятся к этому товару и сценарию, уже вернулись к началу аренды и не имеют пересекающейся брони.

Эквивалент основного запроса в понятном SQL:

```sql
SELECT a.id
FROM assets AS a
WHERE a.scenario_id = :scenario_id
  AND a.product_id = :product_id
  AND a.available_from <= :start_date
  AND NOT EXISTS (
    SELECT 1
    FROM reservations AS r
    WHERE r.asset_id = a.id
      AND r.start_date < :end_exclusive
      AND r.end_exclusive > :start_date
  )
ORDER BY a.id
LIMIT :quantity;
```

Имена с двоеточием обозначают связанные параметры SQLAlchemy, а не вставку текста пользователя в SQL. `NOT EXISTS` означает, что не должна существовать мешающая бронь.

В форме 17-20 означает четыре дня. В базе это `[17, 21)`: с начала 17-го до начала 21-го. Поэтому новая аренда с 21-го не пересекается с предыдущей. А доступность только с 17-го не подходит для заказа на 2-20, даже если конец периода совпадает.

После выборки:

```python
missing = item.quantity - len(available)
```

Найденным единицам создаются брони. Если `missing > 0`, создаются заявка и событие дефицита. Новые физические единицы от этого не появляются.

## 5. Почему нельзя просто проверить остаток и записать заказ

Представьте два одновременных запроса: оба увидели одну свободную единицу и оба решили забрать её. Обычная проверка перед записью сама по себе не защищает от этого.

Поэтому в начале `place_order` блокируется строка сценария. Следующий заказ этого сценария ждёт, пока первый зафиксирует результат. Дополнительно база содержит:

```sql
EXCLUDE USING gist (
  asset_id WITH =,
  daterange(start_date, end_exclusive, '[)') WITH &&
)
```

Смысл ограничения: у одинакового `asset_id` диапазоны не должны пересекаться. `&&` является оператором пересечения диапазонов PostgreSQL; `btree_gist` добавляет поддержку сравнения UUID в таком индексе.

Заказ, его позиции, брони и заявки находятся в одной транзакции. Если вставка события падает, предыдущие вставки этого заказа откатываются. Успешный ответ отправляется только после фиксации, не до неё.

## 6. Где SQL полезен для аналитики

В `operations.py` запрос `STOCK_SQL` вычисляет складскую сводку. Он использует `WITH`, `JOIN`, `NOT EXISTS`, группировку и агрегаты. Для каждой единицы ищется ближайшая свободная дата с учётом исходного возвращения и существующих броней.

Простой пример статистики по сценарию:

```sql
SELECT p.name, COUNT(a.id) AS total
FROM assets AS a
JOIN products AS p ON p.id = a.product_id
WHERE a.scenario_id = :scenario_id
GROUP BY p.id, p.name
ORDER BY total DESC;
```

Первый учебный шаг: понять, почему тут нужен `GROUP BY`. Следующий: добавить к сводке число недостающих единиц из `purchase_requests`, не удваивая суммы из-за соединения нескольких таблиц.

## 7. В каком порядке разбирать

1. `schemas.py`: что принимаем и что считаем ошибкой.
2. `main.py`, маршрут заказа: откуда пришли данные и где открылась транзакция.
3. `booking.py`: пройти один заказ руками, записывая значения переменных.
4. `models.py` и SQL-миграция: связать каждую вставку с таблицей.
5. `tests/test_api.py`: сопоставить продуктовые требования с проверками.
6. `operations.py`: разобрать складскую сводку после базового SQL.

## 8. Проверка понимания перед собеседованием

- Объяснить разницу между моделью товара, физической единицей и бронью.
- Предсказать результат для дат 1-10, 17-20 и 2-20 без запуска.
- Показать, где проверяется запрет аренды в текущем месяце и почему одного календаря недостаточно.
- Объяснить, что случится при потере ответа после сохранения заказа.
- Изменить день возврата с 17-го на 19-е и обновить соответствующие тесты.
- Изменить правило количества и найти все затронутые проверки в Python, SQL и интерфейсе.
- Показать тест отката и объяснить, какие таблицы должны остаться без нового заказа.
- Назвать ограничения проекта: нет настоящих поставок, ролей сотрудников, отмен и реального коммерческого использования.

Достаточно сначала уверенно пройти один заказ от формы до таблиц. Остальная архитектура станет понятнее после этого, а не до.
