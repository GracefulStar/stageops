# Запуск и размещение

## Полный локальный запуск

Из корня проекта при установленном Docker Compose:

```sh
docker compose up --build
```

Сервисы: `db` запускает PostgreSQL 16, `migrate` применяет схему, `app` запускает FastAPI. Приложение слушает только локальный порт 8000; база наружу не опубликована. Интерфейс, API и cookies используют один адрес.

| Адрес | Назначение |
| --- | --- |
| `http://localhost:8000/` | Заказ оборудования |
| `http://localhost:8000/operator` | Склад и заявки текущего браузера |
| `http://localhost:8000/docs` | Интерактивное описание API |
| `http://localhost:8000/healthz` | Проверка приложения и соединения с базой |

Настройки Compose показаны в корневом `.env.example`. Без файла `.env` действуют локальные демонстрационные значения. Реальные пароли не нужно коммитить.

Остановка: `docker compose down`. Данные остаются в именованном томе. Удаление тома через `down -v` уничтожит базу, поэтому для обычного перезапуска это не требуется.

## Без Docker

Нужны Python 3.12+, `uv`, Node.js 24 и отдельная работающая PostgreSQL с расширением `btree_gist`. В корне соберите браузерную часть:

```sh
npm ci
npm run build:frontend
uv sync --project backend --frozen
```

Затем из папки `backend`, с адресом собственной локальной базы:

```sh
export STAGEOPS_DATABASE_URL='postgresql+psycopg://stageops:stageops@localhost:5432/stageops'
export STAGEOPS_ALLOWED_ORIGINS='["http://localhost:8000"]'
uv run alembic upgrade head
uv run uvicorn stageops.main:app --host 127.0.0.1 --port 8000
```

Либо задайте настройки в `backend/.env` по примеру `backend/.env.example`. Приложение не создаёт таблицы при импорте: перед первым запуском обязательна миграция. При старте оно идемпотентно добавляет каталог; парк браузера создаётся при первом запросе каталога.

Если порт занят, выберите другой одновременно для Uvicorn и `STAGEOPS_ALLOWED_ORIGINS`. После изменения React/CSS повторите `npm run build:frontend`; для изменения Python пересборка интерфейса не нужна.

## Публичная Python-версия

В репозитории есть Dockerfile, но сервер и база в интернете ещё не предоставлены. Обычный Python-процесс нельзя разместить внутри текущего Sites Worker. Для постоянного запуска необходим хостинг контейнера и PostgreSQL, поддерживающая `btree_gist`.

Порядок для выбранного хостинга:

1. Создать PostgreSQL. Установить `btree_gist` администратором или разрешить миграционному пользователю создавать расширение.
2. Собрать контейнер из корневого Dockerfile и настроить переменные ниже.
3. Перед запуском новой версии выполнить `.venv/bin/alembic upgrade head` в `/app/backend`.
4. Запустить контейнер на порту 8000 за HTTPS. Health check: `/healthz`.
5. Настроить резервное копирование, ограничение запросов и удаление старых демо-сценариев до привлечения публичного трафика.

| Переменная | Значение |
| --- | --- |
| `STAGEOPS_DATABASE_URL` | Адрес PostgreSQL; требования TLS определяет провайдер базы |
| `STAGEOPS_ALLOWED_ORIGINS` | JSON-массив точных HTTPS-адресов интерфейса без завершающего `/` |
| `STAGEOPS_COOKIE_SECURE` | `true` при HTTPS |
| `STAGEOPS_TIME_ZONE` | `Asia/Tashkent` для текущего календарного правила |

Пароль со специальными символами в URL должен быть URL-encoded. Не используйте локальный пароль из примера для доступной извне базы. Рабочий пользователь приложения не должен иметь административных прав; права на миграции можно выдать отдельно.

### Сохранить существующий адрес StageOps

После размещения Python можно направить существующий интерфейс Sites на его API:

- В настройках окружения Sites задать `PYTHON_API_URL` как HTTPS-origin Python, например `https://api.example.com`, без `/api` и дополнительных путей.
- В Python добавить `https://stageops-rental.kiriyama-issa.chatgpt.site` в `STAGEOPS_ALLOWED_ORIGINS` и включить защищённую cookie.
- Развернуть обновлённую версию Sites с этой настройкой. Клиент продолжит обращаться к своим `/api/catalog`, `/api/orders`, `/api/operations` и `/api/scenario`.

Прокси пересылает cookie, Origin, JSON и ответ сервера. CORS для браузера здесь не требуется: клиент работает с одним адресом. Заголовок ответа `X-StageOps-Backend: python-fastapi` позволяет проверить, что запрос обслужил Python.

При ошибке прокси возвращает 503, а не переключается на прежнюю базу. Заказы D1 остаются в старом прототипе, автоматической миграции данных нет. До настройки реального Python-хоста текущая публичная демонстрация продолжает работать на TypeScript.

## Полная проверка на PostgreSQL

Сначала соберите интерфейс и установите зависимости. Затем укажите **тестовую**, не рабочую базу:

```sh
export STAGEOPS_TEST_DATABASE_URL='postgresql+psycopg://postgres:stageops-test@localhost:5432/stageops_test'
backend/.venv/bin/pytest backend/tests -q
```

Тесты создают случайную схему `stageops_test_<uuid>`, применяют миграцию и удаляют только свою схему. Они не очищают другие схемы и не удаляют общую `btree_gist`.

Без этой переменной SQL-интеграционные тесты пропускаются; это не считается успешной проверкой базы. `.github/workflows/python.yml` задаёт PostgreSQL 16 для полного набора, включая блокировки при одновременных запросах.
